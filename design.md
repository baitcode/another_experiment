# Assumptions

I assume that storing user credentials for platform access (such as tg) is out of scope of this task. I imply that there is a credentials service outside of this one that holds them and lets my service act on behalf of users.

I assume that this API is for internal usage so authorisation is done via jwt-tokens and is service level authorisation. (debatable, can be simplified). Responses for authentication failures (401, 403) and rate limiting (429) are out of scope of this document.

As all media platforms are very different,
their posts are identified differently and 
workflows to fetch and reply to comments are also
very different. I decided not to unify endpoints. Thus every media platform will have its own API namespace, and probably its own version.

I am providing implementation example for Telegram.

Telegram stories are out of scope.

Replies sent through this service are stored as comments: a telegram_comments row with reply_to pointing at the comment it answers and the account's own author fields. The next sync sees the same message and skips it, since a row already exists for its (post_id, telegram_message_id). Replies the account makes from a Telegram client arrive through the sync the same way. There is no flag for the account's own comments; the consumer knows the username and matches it against author_username.

I assume that the same service that holds user authorisation data also holds the credentials for the media platform, in this case the Telegram MTProto session. The session stays there and is never stored by this service; the Telegram library below is the programmatic API through which this service uses it.

This api does not check for data ownership this should be checked by the consumer.

All ids issued by this service are UUID version 7, generated by the database at insert time so that one clock orders them. Id order is insertion order, primary key inserts append at the end of the index, and the comment listings page by id, see List comments.

Post deletion through this API is in scope but it does not delete the post in telegram, it stops comment syncing for a post; comments are never deleted through it. Edits and deletions that happen on Telegram are not tracked by the sync. They are noticed only when the account replies to a comment: the reply handler re-reads its target first and refuses to answer one that was deleted or edited since it was stored, updating the row either way, see Reply step 3. Deletion is soft everywhere and keeps a deleted_at field. Soft-deleted posts and comments are not filtered out of read endpoints: they are returned with deleted_at set, and the consumer decides how to show them. Writes still refuse them: replying to a deleted comment, or on a deleted post, is 404. Submitting the url of a deleted post restores it.

Deleted comments stay in listings, so a deleted parent still appears in the comment listing and its replies stay reachable through the replies endpoint. A reply whose parent was deleted on Telegram before it was ever ingested keeps reply_to null and lists as a top-level comment. Accepted.

Telegram answers getDiscussionMessage with the same MSG_ID_INVALID when the channel has no linked discussion group and when the message id has no discussion thread, because it does not exist or was posted before the group was linked. The library tells the two apart by reading the channel's linked chat: no linked chat is NoDiscussionGroup, otherwise MessageNotFound. Both reject the submit with 400, each under its own code, since nothing could ever be synced: the comment thread of a channel post is the reply thread of the copy Telegram forwards into the linked group when the post is published, and linking a group later forwards new posts only, so a post published without a group never gets a thread and the owner has to repost it. This is checked for channel posts only, where the call is made anyway; a bad message id in a supergroup or forum link passes submit and fails on the first sync run, as the forum links below do. A post's thread therefore never moves, and the job's is_active is set to false in two cases only: a run finding the account unusable, SessionInvalid or UserNotFound, and post deletion.

Links to a message inside a forum topic that is not the topic root, t.me/<group>/<topic_id>/<id> with id different from topic_id, are rejected as malformed_url. Telegram keeps no thread for such a message, so its replies cannot be fetched with getReplies. Decision: no special error code for this case. A two-segment link into a forum, the form Telegram itself produces for a topic, is accepted as a topic root; the url cannot prove that, so a link to an ordinary message inside a topic passes submit and fails on its first sync run, with the reason in sync_error.

For now I restrict the content that is being sent as content to text only. I don't want to deal with embedded images. (it might be easy if those are sent as base64encoded content, I just want to narrow the research surface)

For some reason I decided to do an endless pagination (you can't pick page, but can load more)

Post search is outside of this spec's scope, but should probably live somewhere here.

# Telegram library

The service never calls MTProto directly. An internal library wraps it behind six calls and a small error set. The service never sees a session and never string-matches a Telegram error.

## Binding

```text
client = telegram.for_user(username)
```

The library runs as a process of its own, one per deployment; the API handlers and the sync worker call into it, and `for_user` is a handle on that process, not a connection held by the caller. The library obtains the account's MTProto session from the credentials service, connects, and reuses the connection. Session storage and refresh stay with that service; the library hides logic of managing tg account connections with calls serialised on it (two concurrent users of one session cause AUTH_KEY_DUPLICATED, which is why the connection lives in one process however many API or worker processes call it, and why their calls for one account queue behind each other), reconnects, data centre migration, peer access hashes, and stripping a -100 prefix from any id a caller passes. `for_user` raises `UserNotFound` when the credentials service has no session for the username, and `Upstream` when that service cannot be reached.

## Methods

All ids are bare integers, all dates UTC.

```text
resolve_peer(ref) -> Peer
    ref:  a username or a bare channel id
    Peer: { chat_id, kind: 'channel' | 'supergroup' | 'forum' }
    Submit step 2, for every url form; numeric forms still need the peer's kind.

resolve_user(username) -> User
    User: { id, name }
    Reply step 4, the acting account's own profile, so a reply row carries the same author fields the sync
    would have written. Raises PeerNotFound if the username does not resolve to a user.

get_discussion_thread(channel_id, message_id) -> Thread
    Thread: { chat_id, root_message_id }
    Submit step 3, channel posts only. On MSG_ID_INVALID the library reads the channel's linked chat from
    getFullChannel: none raises NoDiscussionGroup, otherwise MessageNotFound, since the group exists and it is
    the message that has no thread.

get_thread_messages(chat_id, root_message_id, min_id, limit) -> Page
    Page:    { messages: [Message] }
    Message: { id, reply_to_message_id, author: { id, username, name } | null, text, posted_at, edited_at | null }
    reply_to_message_id is never null: a top-level comment answers the thread root. edited_at is Telegram's
    edit date.
    Run step 2. Wraps getReplies and its 100-per-call ceiling; the caller passes the last id it has
    and takes one page per run; whatever is left waits for the next run. Messages come back in ascending id order.

get_messages(chat_id, ids) -> [Message | Deleted]
    Deleted: { id }
    Reply step 3, at most 100 ids per call. Wraps getMessages on the chat that holds the thread. A message
    Telegram no longer returns, deleted or no longer visible to the account, comes back as Deleted, and the
    service treats both as deleted: a reply attempted while the account temporarily cannot see the chat marks
    its target deleted for good. Accepted. Order is not guaranteed, the caller matches by id.

send_reply(chat_id, reply_to_message_id, text, topic_id = null) -> Sent
    Sent: { message_id, posted_at }
    Reply step 4. topic_id becomes top_msg_id for forum posts.
```

## Errors

| Library error | Raised by | Service behaviour |
|---|---|---|
| `UserNotFound` | for_user | 404 `user_not_found` on submit and reply; sync: as `SessionInvalid`, written to `sync_error` and the job is disabled |
| `PeerNotFound` | resolve_peer | 400 `channel_not_found` |
| `PeerNotFound` | resolve_user | 502 `upstream_failure`: the bound account's own username failing to resolve is not a client error |
| `NoDiscussionGroup` | get_discussion_thread | 400 `no_discussion_group`: the channel has no linked group, and linking one later gives an existing post no thread |
| `MessageNotFound` | get_discussion_thread, send_reply, get_thread_messages | 400 `message_not_found` on submit; 404 `comment_not_found` on reply, and the comment is marked deleted; `sync_error` on sync |
| `Forbidden` | send_reply | 502 with the reason, until a 403 mapping is in scope |
| `FloodWait(retry_after)` | any | submit and reply: 500 `flood_wait` carrying `retry_after`, 429 with Retry-After once rate limits are in scope; sync: written to `sync_error`, the job comes round again in its turn |
| `SessionInvalid` | any | the user revoked the session. submit and reply: 500 `session_invalid`; sync: written to `sync_error` and the job is disabled |
| `Upstream` | any | 502 `upstream_failure`, raw message in `upstream_error` |

## Deliberately absent

No history fetch beyond a thread, no sweep over known messages, and no subscription to Telegram's update stream. The sync only moves the high-water mark forward; an edit or deletion is found when the reply handler re-reads its single target through `get_messages`, so there is no persistent listener and no per-chat pts bookkeeping. The update stream would catch edits and deletions as they happen and is the upgrade path if that comes to matter.

# Database schema

PostgreSQL 18 or later, for `uuidv7()`. All ids are UUIDv7, assigned by the database on insert. `username` is the Telegram account on whose behalf the service acts when syncing and replying; it is an attribute of the post, not an access scope. No credentials are stored (see Assumptions).

## Platform specific

### Posts

```sql
create table telegram_posts (
    id                      uuid primary key default uuidv7(),
    username                text not null,

    -- for UI
    title                   text not null,
    url                     text not null,

    -- parsed from url
    post_type               text not null
                            check (post_type in ('channel', 'forum', 'supergroup')),             

    message_id              bigint not null,    
    channel_id              bigint not null, -- bare id as in t.me/c/ links and MTProto, never the -100 Bot API form (prefix stripped on parse);
                                             -- resolved in the submit handler for username url forms
    forum_topic_id          bigint,          -- set from post_type, not from the url: message_id for a forum post, since only
                                             -- topic roots are accepted and a topic's root id is its topic id; null otherwise

    -- channel posts only, resolved in the submit handler via the library's get_discussion_thread: the linked discussion
    -- group and the auto-forwarded copy of the post, which is where the comment thread lives; fixed when the post is
    -- published, so never rewritten. Null for supergroup and forum posts, whose thread is in channel_id itself, rooted
    -- at message_id (supergroup) or forum_topic_id (forum)
    discussion_chat_id      bigint,
    discussion_message_id   bigint,          

    -- syncing metadata
    last_synced_at          timestamptz,     -- last successful sync; returned as comments_synced_at
    last_synced_message_id  bigint,          -- high-water mark for incremental fetch
    sync_error              text,            -- last sync error

    -- bookkeeping
    created_at              timestamptz not null default now(),
    updated_at              timestamptz not null default now(),
    deleted_at              timestamptz 
);

-- one tracked post per account; different url forms of the same post collapse because channel_id is always resolved.
-- covers all post types: for forum and supergroup posts channel_id is the group id, and message ids are
-- unique per chat regardless of topic, so forum_topic_id is not part of the key
create unique index telegram_posts_username_channel_message_uniq
    on telegram_posts (username, channel_id, message_id);
```

## Common

### Comment sync jobs and runs

```sql
-- one persistent row per post; created on submit, never deleted
create table post_comments_sync_jobs (
    id                      uuid primary key default uuidv7(),
    post_id                 uuid not null,
    platform                text not null check (platform in ('telegram')),

    -- true: scheduler keeps picking it up forever, ordinary failures included; false: post sync is disabled.
    -- set false by a run on SessionInvalid or UserNotFound and by post deletion
    is_active               boolean not null default true,

    -- lease. locked_at is when the job was last picked and is never cleared: the scheduler orders by it, so
    -- picking is round-robin with never-picked jobs first. locked_until is the lease expiry, set on pick, pushed
    -- forward by the run while its upstream call is in flight, and cleared on release; a lease that expired
    -- without release is stale and the job is eligible again
    locked_at               timestamptz,
    locked_until            timestamptz
);

-- one job row per post
create unique index post_comments_sync_jobs_platform_post_uniq
    on post_comments_sync_jobs (platform, post_id);

-- scheduler walks active jobs in pick order, least recently locked first, and skips the ones whose lease is held.
-- the pick needs nothing from telegram_posts
create index post_comments_sync_jobs_due_idx
    on post_comments_sync_jobs (locked_at asc nulls first)
    where is_active;
```

```sql
-- one row per sync run, inserted when the run starts and completed when it finishes; never updated after that.
-- grows without bound under endless polling; retention is accepted as out of scope for this design
create table post_comments_sync_runs (
    id                      uuid primary key default uuidv7(),
    post_id                 uuid not null,
    platform                text not null check (platform in ('telegram')),
    job_id                  uuid not null references post_comments_sync_jobs (id),

    started_at              timestamptz not null,
    finished_at             timestamptz,         -- null while the run is in progress
    status                  text not null default 'running'
                            check (status in ('running', 'success', 'failure')),
    error                   text                 -- null on success
);

-- latest runs per post, for audit and debugging; started_at is never null so the order is total
create index post_comments_sync_runs_post_idx
    on post_comments_sync_runs (post_id, started_at desc);
```

# Notes

## Submit post

1. Parse the url. Reject with 400 if it matches no supported form, links to a specific comment (`?comment=`), or points inside a forum topic at anything but the topic root.
2. Bind `telegram.for_user(username)` and call `resolve_peer` with the username or bare id from the url. `UserNotFound` from the bind is 404 `user_not_found`; `PeerNotFound` is 400 `channel_not_found`; `Upstream` is 502; `SessionInvalid` and `FloodWait`, from any call in steps 2 and 3, are 500. The returned `kind` becomes `post_type`; the url alone cannot tell a channel from a supergroup. `forum_topic_id` follows from `kind`, not from the url: `message_id` for a forum, null otherwise, so a topic segment in a url to a non-forum peer is ignored and a two-segment url to a forum is taken as a topic root.
3. For a channel post, call `get_discussion_thread(channel_id, message_id)` and store the result as `discussion_chat_id` and `discussion_message_id`. `NoDiscussionGroup` means the channel has no linked group: return 400 `no_discussion_group` and store nothing; the post has no thread, and linking a group later will not give it one, so the owner has to repost. `MessageNotFound` means the group exists but Telegram keeps no thread for this message id, because it does not exist or predates the link: return 400 `message_not_found` and store nothing. Either way a resubmit of a tracked post, whose channel has since lost its group or whose copy is gone, leaves the post as it is. Supergroup and forum posts get no such check at submit; a bad message id there surfaces in `sync_error` on the first run.
4. Insert the post. The unique index on (username, channel_id, message_id) is the only duplicate check. On conflict, return 200 with the existing id after two repairs in one transaction: if the post is soft-deleted, clear `deleted_at`; if its job is disabled, set it active and clear `sync_error`. For a channel post, step 3 has just resolved the thread again and returned the pair already stored, since a post's thread is fixed when it is published; nothing is written from it.
5. Insert the sync job, active. Return 201.

The worker never resolves anything and never sees a duplicate post; duplicate messages are the sync's on-conflict path.

## Get post

Read the post by id; a soft-deleted post is returned with `deleted_at` set, only an unknown id is 404. Join its sync job. Fields map one to one: `comments_synced_at` is `last_synced_at`, `comment_sync_enabled` is `is_active`, `sync_error` keeps its name.

`comments_synced_at` is the last success and `sync_error` the last failure, and they are read together. Both null: no run has happened yet. `sync_error` set and `comments_synced_at` null: nothing has succeeded yet, every run so far failed. Both set: the last run failed after an earlier success, and the comments are as of `comments_synced_at`.

## Delete post

Load the post by id; only an unknown id is 404. In one transaction set `deleted_at` to now if it is null and the job's `is_active` to false, then return 200 with `deleted_at`. Deleting a deleted post changes nothing and returns the same body. Comments are kept, and get post, list comments and list replies keep serving the post with `deleted_at` set. A run already in flight finishes on its own and releases its lease; the job is not picked again, since the scheduler reads `is_active`. Submitting the post's url again restores it, see Submit post step 4.

## List comments

Page by `id`, ascending. Ids are UUIDv7 assigned by the database on insert, so a row inserted after a cursor was handed out sorts after it, whichever path inserted it, and load-more never skips a row. `telegram_message_id` would not do: a reply sent through this service gets a Telegram id above a comment the sync has not ingested yet, and a cursor taken past the reply would skip that comment once it arrives. The order is therefore ingestion order: Telegram order within a sync page, with a reply sent here placed when it was sent rather than by `posted_at`; every item carries `posted_at` for a consumer that wants to sort. The one gap left is a listing read between the commits of two insert transactions that overlapped, when the later commit carries the smaller ids; the window is the length of Run step 3's transaction, accepted. The cursor is base64 of `{"after": <id>}`. The listing is top level only, rows with `reply_to` null, and the partial index on (post_id, id) where `reply_to` is null serves the query. Nested replies come from the replies endpoint.

Rows with `deleted_at` set are returned like any other, with the field exposed and the last known text, so a deleted parent never hides its replies; `edited_at` is exposed the same way. A soft-deleted post still lists its comments; only an unknown post id is 404. `author_id` is sent as a string to avoid precision loss.

Each item carries `has_replies`, computed as an exists over the partial index on (reply_to, id), one probe per row on the page. There is no flag for the account's own comments: the consumer knows the post's `username` and matches it against `author_username`. Replies the account makes outside this service arrive through the sync like any other comment.

## Reply

1. Validate the text: empty, too long, or invalid character gives 400. Telegram is not called yet.
2. Load the post, then the comment by (id, post_id). A soft-deleted post is 404 `post_not_found`. A deleted comment is 404 `comment_not_found` with the "was deleted" message. Sync being disabled does not block a reply. `chat_id` depends on `post_type`: `discussion_chat_id` for a channel, `channel_id` for a supergroup or forum. `topic_id` is `forum_topic_id` for a forum, null otherwise.
3. Bind `telegram.for_user(post.username)` and re-read the target: `get_messages(chat_id, [telegram_message_id])`. The sync never re-reads a message it already has, so the reply checks its target for itself, and the row is brought up to date before the request returns, whichever way it goes:
   - `Deleted`: set the comment's `deleted_at` to now and return 404 `comment_not_found` with the "was deleted" message.
   - a message whose `edited_at` differs from the row's: write its `text` and `edited_at` to the row and return 409 `comment_edited` with the refreshed comment item in the body. The consumer sees what it is now answering and retries; the retry compares equal and goes through.
   - the same `edited_at`: the comment is as stored, continue.
   This step fails before anything is sent, so a refused reply leaves no message on Telegram.
4. Call `resolve_user(post.username)` for the account's id and name, then `send_reply(chat_id, telegram_message_id, text, topic_id)`.
5. `MessageNotFound` from `send_reply` is 404 `comment_not_found` and also sets the comment's `deleted_at`: the target went between the re-read and the send, and Telegram has just refused it as gone. `UserNotFound` from the bind in step 3 is 404 `user_not_found`; `Forbidden` and `Upstream` are 502; `SessionInvalid` and `FloodWait`, from any call in steps 3 and 4, are 500. `PeerNotFound` from `resolve_user` is 502 as well, and since it is raised before `send_reply`, nothing was posted.
6. Insert a `telegram_comments` row: the post id, the returned `message_id` as `telegram_message_id`, the comment's id as `reply_to` and its `telegram_message_id` as `reply_to_message_id`, the text, the returned `posted_at`, `post.username` as `author_username` and the id and name from `resolve_user` as `author_id` and `author_name`. On conflict on (post_id, telegram_message_id) the sync got there first and its row is complete, so use that row. Return 201 with the row in the comment item shape. The next sync sees the same message and skips it. If the insert fails after Telegram accepted the message, the sync ingests the reply on its next run. Accepted.

## List replies

Load the comment by (id, post_id); only an unknown id is 404, a deleted comment still lists its replies. Select the `telegram_comments` rows whose `reply_to` is the comment's id, direct children only, paged by `id` ascending, as for comments. The cursor is base64 of `{"after": <id>}`, and the partial index on (reply_to, id) serves the query. Items have the comment item shape, the same as in the comment listing and the reply endpoint's 201 body, and include replies from anyone, not only those sent through this service.

## Sync worker

A scheduler loop over `post_comments_sync_jobs`, and one run per picked job. The scheduler only picks. A run touches the post, adds new comments, writes its run row, and can extend the lease on its job; on `SessionInvalid` or `UserNotFound` it also disables the job.

Scheduler, each tick: pick a batch of active jobs whose lease is free or expired, least recently locked first, and take the lease in the same statement. A never-locked job sorts first, so a new post gets its first run promptly; after that picking is round-robin.

```sql
update post_comments_sync_jobs j
   set locked_at = now(), locked_until = now() + $lease_timeout
 where j.id in (
       select id from post_comments_sync_jobs
        where is_active and (locked_until is null or locked_until < now())
        order by locked_at asc nulls first
        limit $batch_size
        for update skip locked)
returning j.id, j.post_id, j.platform;
```

Then launch a run for each returned job as a background task. A run is one upstream call followed by a short transaction, so the lease timeout is sized for a normal call. A run extends the lease while the call is in flight: a heartbeat pushes `locked_until` forward by `$lease_timeout` whenever less than half of it is left, so a slow call, such as one queued behind other calls on the same account connection, does not get the job picked twice. The extension is guarded by `locked_until > now()`; a lease that already expired is not revived, the run still finishes, and if the job was picked again meanwhile the second run's inserts are no-ops on conflict.

Run, per job:

1. Open a run row as `running`.
2. Bind `telegram.for_user(post.username)` and call `get_thread_messages(chat_id, root_message_id, min_id, 100)` once, with `min_id = last_synced_message_id`. The thread depends on `post_type`: (`discussion_chat_id`, `discussion_message_id`) for a channel, (`channel_id`, `message_id`) for a supergroup, (`channel_id`, `forum_topic_id`) for a forum. A run takes one page; the next run continues from the new high-water mark. A thread with a backlog therefore catches up 100 comments per run, so a thread of N comments needs N/100 runs. The lease heartbeat covers this call.
3. On success, in one transaction: insert the messages on (post_id, telegram_message_id) with `on conflict do nothing`: a reply sent through this service is already there, and a row already known is left as it is. New rows take `edited_at` from the message. Then set `reply_to` on the new rows by joining `reply_to_message_id` to the post's comments on `telegram_message_id`; the thread root is not a comment row, so top-level comments stay null. A parent always has a lower id than its reply and pages ascend, so it is in an earlier page or earlier in this one; a parent that never came through leaves `reply_to` null. Set `last_synced_message_id` to the largest id in the page, unchanged if the page is empty; set `last_synced_at`; clear `sync_error`. The run stays open.
4. Close the run as `success` and release the lease by clearing `locked_until`.
5. On any library error, in one transaction: write it to `sync_error`, close the run as `failure`, release the lease; what step 3 committed stays. On `SessionInvalid` or `UserNotFound` also set the job's `is_active` to false, since retrying cannot help until the user is back in the credentials service with a valid session.

There are no retries; the job comes round again in its turn.

# Open todo

- No backoff in the sync path. A job that hits `FloodWait`, or a thread that fails for good, such as one whose root was deleted on Telegram, is eligible again on the next tick and fails again in its turn, forever. `retry_after` is written to `sync_error` and otherwise discarded, and all jobs of one account share a serialised connection, so they walk into the same wait one after another. The tick interval, the batch size and a per-job minimum interval are not defined either. Candidate: a `not_before` on the job, set from `retry_after` on `FloodWait` and pushed out on repeated failures, and honoured by the pick.
